## まず押さえる

1. **リポジトリの正体**: 実体は `README.md` (737 行の注釈付きリンク集) + `templates/` の 4 テンプレート + `verify_urls.py` (URL 到達性検証スクリプト)。それ以外の情報はすべて外部リンク。本文を読みたいものはローカルには無く、URL 先を見る必要がある。README 冒頭の定義文の直前と、`Skills & MCP` / `Verification & CI Integration` 等のセクション冒頭には、Claude Code 用 skill をカテゴリ別に並べた agentcraft.dev への誘導リンクがある (外部の skill カタログで、エントリではない)。
2. **定義** (`README.md` 冒頭): "Harness engineering is the discipline of designing the scaffolding — context delivery, tool interfaces, planning artifacts, verification loops, memory systems, and sandboxes — that surrounds an AI agent and determines whether it succeeds or fails on real tasks"。焦点はモデルではなくハーネス。
3. **中心原則**: "Every component here exists because the model can't do it alone — and the best harnesses are designed knowing those components will become unnecessary as models improve"。`templates/HARNESS_CHECKLIST.md` の「When this harness component should be removed」表 (Component / Exists because / Can be removed when) がこの原則を運用に落としている。Foundations の Marmelab "The State Of AI Harness Engineering 2026" (2026 年 9 月) も、統制に expiry condition を持たせてモデル向上に合わせハーネスを graceful に腐らせることを推奨している (README の注記ベース、記事本文は未検証)。`Context Delivery & Compaction` の Boris Cherny の YC Startup School 講演 (2026 年 7 月) はこれを実測で裏づける: Opus 5 出荷時に Claude Code の system prompt の約 80% を、モデルがもう持たない挙動への補正だったとして削除し、eval の退行は無かった。手法は「prompt を全部剥がし、繰り返す失敗を直す行だけ足し戻す」をモデルのリリースごとに繰り返す ablation で、蓄積した指示は「モデル能力に対する賭け」であり古びる (harness rot) という主張 (README の注記ベース、講演本体は未検証)。
4. **分類原則** (`AGENTS.md`): セクションは vendor 別ではなく「解決する問題」別に編成する。各エントリは `- [Title](URL) — 1–2 sentence note` 形式で、note は「なぜ読む価値があるか」を opinionated に書くのが規約。
5. **`templates/AGENTS.md`**: プロジェクトレベルのエージェント指示テンプレート。要点は tool permissions を Allowed / Restricted (ask before proceeding) / Not allowed の 3 段で明示することと、タスク完了前の Verification gates (tests / linter / 変更範囲) をチェックリスト化すること。"agents perform better with clear boundaries than vague restrictions" とコメントで明言。
6. **`templates/PLAN.md` + `templates/IMPLEMENT.md`**: 長時間タスク用のペア artifact。PLAN.md は milestone ごとに `verify: <command>` を付け scope boundaries (in/out) を書く。IMPLEMENT.md は append-only の実装ログで、Deviations summary (Deviation / Reason / Plan updated?) と Open questions を追跡。OpenAI の "Run Long-Horizon Tasks with Codex" が示す Plan.md/Implement.md パターンのテンプレート化。
7. **Foundations の起点**: 先頭は Mitchell Hashimoto "My AI Adoption Journey" (https://mitchellh.com/writing/my-ai-adoption-journey, 2026 年 2 月) で、README は "harness engineering" の語を作った essay と位置づける。6 段階の導入経路の終点がハーネス自体の engineering で、agent の失敗 1 件ごとに AGENTS.md の 1 行か専用 tool で恒久的に塞ぎ、同じ失敗クラスを再発させない。Ghostty で修正が必要な commit が 3 か月の蓄積で 40% → 3% に下がったという数値が「信頼性の面は prompt でなくハーネス」の根拠 (README の注記ベース、記事本文・数値は未検証)。続いて OpenAI "Harness Engineering" (https://openai.com/index/harness-engineering/)、Anthropic "Building Effective Agents" (https://www.anthropic.com/research/building-effective-agents)、Anthropic "Harness Design for Long-Running Application Development" (https://www.anthropic.com/engineering/harness-design-long-running-apps)、Martin Fowler "Harness Engineering" (https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html) などが並ぶ (並び順はこの順ではない)。ハーネス設計を「分野」として定義する canonical essays としてリストの起点に置かれている。同セクション末尾には `lopopolo/harness-engineering` (https://github.com/lopopolo/harness-engineering) が加わり、再利用可能な `AGENTS.md`/`CLAUDE.md` 成果物・playbook・eval・ドメインモデリング文書を束ねた OSS の anthology + agent context bundle として位置づけられている (README の注記ベース、中身は未検証)。ハーネス成果物そのものを探すならここが最初の当たり先。
8. **ハーネスの構造分解**: LangChain "The Anatomy of an Agent Harness" (https://blog.langchain.com/the-anatomy-of-an-agent-harness/) は filesystem / code execution / sandbox / memory / context management の 5 primitives に分解。arXiv 論文 "What makes a harness a harness" (https://arxiv.org/abs/2606.10106) は agent loop / tool interface / context management / control mechanisms の 4 要素を必要十分条件として定義。その直後の arXiv "AI Harness Engineering: A Runtime Substrate for Foundation-Model Software Agents" (https://arxiv.org/abs/2605.13357, 2026 年 5 月) は、構成的定義を補う運用側の成熟度モデル: task specification / verification / failure attribution など 11 の部品責務を、agent に見せる runtime 支援を段階的に増やす 4 段の ladder (H0–H3) に落とし、実行を監査可能な episode file に梱包する trace ベースのプロトコルを付ける。上の段ほど裸の patch ではなく再現ログ・決定論的な要件チェック・構造化された検証レポートを出す (README の注記ベース、論文本文は未検証)。Foundations 末尾の arXiv "Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents" (https://arxiv.org/abs/2609.00006, 2026 年 7 月) は定義でなく実コードの側: Claude Code / Codex CLI / Gemini CLI / OpenHands / Aider / OpenCode / OpenClaw など 11 の本番ハーネスのソースを 7 つの canonical subsystem で解剖し、13 の横断的観察・29 の設計パターン・18 の設計推奨・90 行の最小ハーネス scaffold を出す。約 400 万行を見ても汎用 agentic framework を import する runtime も、vector embedding でコードを検索する runtime も無く、本番ハーネスは手書きの async loop と決定論的 retrieval で動いている。同じ 8 システムを 1 四半期後に再 pin して source diff した縦断サンプルでは、収斂が模倣に変わり、挙動の方針が prompt の散文から configuration へ移っていた (README の注記ベース、論文本文は未検証)。
9. **「ハーネスだけで性能が動く」実証系**: LangChain "Improving Deep Agents with Harness Engineering" (https://blog.langchain.com/improving-deep-agents-with-harness-engineering/) はモデル交換なしのハーネス変更のみで Terminal Bench 2.0 のランクを 30 位から top 5 に改善した事例。LangChain "Tuning the harness, not the model" (Nemotron 3 Ultra playbook, https://blog.langchain.com/tuning-the-harness-not-the-model-a-nemotron-3-ultra-playbook, 2026 年 7 月) は harness-only tuning で Nemotron 3 Ultra を Deep Agents 上で Opus 4.8 の 1 point 差まで、約 1/10 のコスト ($4.48 vs $43.48) で到達させ、「evals はハーネス作業の訓練データ」「モデルの生の能力でなく fit が品質を決める」を実証。deepset "Harness Engineering" (https://www.deepset.ai/blog/harness-engineering) も failure 分類 (context / constraint / verification / planning) を各ハーネス部品に対応付ける同趣旨の synthesis。評価方法論の側では、`Evals & Verification` の position paper "Stop Comparing LLM Agents Without Disclosing the Harness" (https://arxiv.org/abs/2605.23950, 2026 年 5 月) が「Binding Constraint Thesis」(frontier モデル間の long-horizon タスクでは context 構築・tool 相互作用・orchestration・verification のハーネス構成がモデル選択より強く性能を縛る) を定式化し、ハーネスの開示基準と、ハーネス起因とモデル起因の分散 (ranking reversal を含む) を分ける分散分解の手順を提案する。Harness-Bench (arXiv 2605.27922) と対で「比較にはモデルだけでなくハーネスを報告せよ」の主張 (README の注記ベース、論文本文は未検証)。
10. **収載基準** (`CONTRIBUTING.md`): (1) specific harness problem に対応する、(2) 読む価値の理由 note が必須、(3) vendor-agnostic by principle (特定モデル依存でもパターンが一般化すれば可)。除外: 一般 AI/ML 論文・ハーネス無関係のモデルベンチマーク・マーケ記事・「モデルの使い方」チュートリアル。
11. **ハーネスと sandbox の内外関係**: "The Agent Harness Belongs Outside the Sandbox" (README `Security, Sandbox & Permissions`, https://www.mendral.com/blog/agent-harness-belongs-outside-sandbox) は agent loop を sandbox の外に置く設計論。credential を untrusted container に入れず、sandbox を suspendable な cattle として扱う。「harness inside」と「harness outside」は実装差でなく別のセキュリティ・信頼性モデルだという主張で、containment 設計 (Anthropic "how we contain Claude" 等) に一段の選択軸を足す。同セクションには OS 側に isolation primitive が無い環境への移植を扱う一次資料 (OpenAI "Building a safe, effective sandbox to enable Codex on Windows", https://openai.com/index/building-codex-windows-sandbox/) も並ぶ。
12. **自然言語ルールは guardrail ではない**: arXiv "When `Do Not` Is Not Deny: Security Rules in CLAUDE.md vs Built-In Controls" (README `Permissions & Authorization`, https://arxiv.org/abs/2608.23550) は公開 `CLAUDE.md` 481 件を分析し、自然言語のセキュリティルールのうち対応する built-in control に裏打ちされているのは約 4% だけと報告。「documented intent と enforced permission の乖離」を数値で示す資料で、CLAUDE.md に「〜するな」と書くだけの禁止事項は決定論的な強制 (permissions / hooks) に写像しない限り guardrail にならない、という主張 (README の注記ベース、論文本文は未検証)。永続メモリでも同じ構図になる: arXiv "When Malicious Instructions Persist" (`Memory & State`, https://arxiv.org/abs/2609.13889, 2026 年 9 月) は、untrusted な内容を coding agent の永続メモリに書き込ませると後のセッションで悪性挙動が起き (Claude Code で injection 66.9% / cross-session 攻撃成功 81.7%、OpenClaw で 73.7% / 55.5%)、benign タスクの性能は変わらないので汚染が見えないと報告。sandwich 型の prompt 防御は汚染後にはほとんど効かず、信頼境界は読み出し側の prompt でなく**書き込み経路**に置く (memory write の provenance チェックと人の承認、加えて retrieval 時の filtering)。同セクションの LangChain Agent Builder の記憶系が全 memory write を HITL 承認にしている理由の裏づけ (README の注記ベース、論文本文・数値は未検証)。
13. **ユーザーが事前に書く permission policy は per-action 承認より弱い**: arXiv "Do User-Authored Permission Policies Improve Protection Against AI Agent Overreach?" (README `Permissions & Authorization`, https://arxiv.org/abs/2608.27443) は非技術者 113 名の user study (2026 年 8 月) で、per-action の HITL 承認・自動モデルレビュー・ユーザー自作の allow/ask/never ルールを比較。事前に書いたポリシーは per-action 承認より overreach の阻止率が約 20 ポイント**低かった**。原因はユーザーが大半のルールを "ask" に設定し、結局その場で承認してしまうこと — 静的な事前コミットが実行時プロンプトに退行し、保護は増えない。項目 12 と合わせると「ルールを書く」層 (CLAUDE.md / settings の allow-ask-deny) だけでは不十分で、permission の UX 設計が実効性を決めるという主張 (README の注記ベース、論文本文は未検証)。逆向きの失敗もある: Faros AI "Why AI Coding Agents Actually Fail" (`Debugging & Developer Experience`, 2026 年 8 月) では、最大の失敗クラスタが「DO NOT MODIFY: Tests」のような定型の禁止文を agent が字義どおりに守りすぎて必要な作業を拒む instruction conflict だった。禁止文は「効かない」だけでなく「効きすぎる」こともあり、範囲を精密に書く必要がある (README の注記ベース、記事本文は未検証)。
14. **subagent に渡す context 量の判断規則**: LangChain "Organizing Context in a Multi-Agent Harness" (README `Context Delivery & Compaction`, https://www.langchain.com/blog/organizing-context-in-a-multi-agent-harness, 2026 年 9 月) は subagent の context mode を 2 つに分ける。`isolated` は新規 context で開始し、context isolation を firewall として使う。`forked` は supervisor の会話全体を継承し、末尾の tool call を除去・task description を user message として書き直し・prompt caching を保つ。判断規則は **進行中の調査を継続する worker は fork、独立に判断すべき verifier は isolate** (README の注記ベース、記事本文は未検証)。
15. **compaction は統制の面でもある**: arXiv "Governance Decay" (README `Context Delivery & Compaction`, https://arxiv.org/abs/2606.22528, 2026 年 6 月) の ConstraintRot ベンチ (1,323 episode, 7 モデル系列) では、ポリシーを全文 context に置くと違反率 0% だが compaction 後は 30% (モデルによって 59%) に上がり、summarizer に正当なポリシーを落とさせる Compaction-Eviction Attack は評価した全モデルに通った。対策の Constraint Pinning (統制制約を lossy な compaction から隔離する、訓練不要) で 0% に戻る。設計規則は「安全上重要な指示は compaction されうる context 領域の外に置く」 (README の注記ベース、論文本文は未検証)。何が落ちるかの実測は arXiv "The Compaction Cliff in Long-Running AI Agent Memory" (同セクション, https://arxiv.org/abs/2608.22752, CIKM 2026): Claude Code の `/compact` prompt (Sonnet 4.6) は安全ルールを 1 回で 53%、5 回で 10% しか保持せず、4 モデル系列・試した全要約戦略で同じ減衰が出た。提案の Knowledge Triage は knowledge 行を型 (constraint / procedural / belief / preference / episodic) に分け型ごとの保持方針に回す — TypeCompact は最強の単発 LLM compactor の 2–4 倍の安全ルールを残し (5 回で recall 96%)、TypeRetrieve は in-scope のルールを relevance より先に pin する (recall@50 100%)。「ルールと episodic log を同じ率で compaction するのは設計バグ」という主張で、54K repo 由来の実 agent 設定約 400K 件のコーパスを公開 (README の注記ベース、論文本文・数値は未検証)。compaction 以前の劣化として、arXiv "Diagnosing and Mitigating Context Rot in Long-horizon Search" (同セクション, https://arxiv.org/abs/2606.29718, GAIR/SJTU) は search agent が解ける問題で諦める・不確かに答える *premature termination* が、window が埋まるずっと前から context の蓄積とともに増えると示す。pruning 実験では履歴を捨てると give-up は消えるが無回答が跳ね、毒は token 数でなく内容の noise。compaction / trimming (discard-all / keep-latest / keep-latest+summarize) / isolation (sub-agent 呼び出し) の 7 手法比較で、compaction と trimming の併用がコストと rot の最良の折り合い、効果はモデル依存が強い (isolation は Qwen3.5 で +19%、GLM-4.7 では負) ので context 方針は backbone ごとに調整し他から流用しない (README の注記ベース、論文本文・数値は未検証)。コスト・記憶の面でも compaction は既定にならない: louisbouchard.ai "Why We Stopped Compacting Our Agent's Context" (同セクション, 2026 年 8 月) は本番 AI tutor (660 turn、仕込んだ事実の probe) で、全履歴保持が記憶 recall 100% / $0.11/turn、compaction 構成が 58% / $0.24/turn。要約が cache 済み prefix を書き換えて cache hit を潰すのが原因。判断枠組みは「まず真の制約を名指しする (window 不足 → retrieval、請求額 → モデル選択、品質劣化 → 的を絞った修正)」で、履歴の書き換えより cache を保つ truncation と tool 出力の上限を優先し、compaction は自動でなく条件付きにする (README の注記ベース、記事本文は未検証)。発火条件の側では arXiv "AutoCompact" (同セクション, 2026 年 10 月) が、token 閾値は暫定策で正しい trigger は意味的なもの (作業が安全な境界にいるか) だとし、その判断を学習で身につけさせる (README の注記ベース、論文本文は未検証)。
16. **鮮度と信頼性の注意**: エントリ数が多く (README 全体で `- [Title](URL)` 形式の外部リンクエントリが約 540。先頭の目次アンカー 9 行は別)、2026 年の新しめの記事・arXiv・小規模リポジトリが大量に混在する。本蒸留は README の注記に基づき、外部 URL の生死や記載内容の真偽は未検証。2026-11 から README 冒頭のバッジの下に「Sponsor this list」(製品を読者の前に出す掲載の申込 issue form) が付いたので、今後のエントリには掲載料を払った製品が混ざりうる。重要判断では URL 先の一次資料を直接確認すること。リンク検証は原典の `verify_urls.py` で行う建て付け。
